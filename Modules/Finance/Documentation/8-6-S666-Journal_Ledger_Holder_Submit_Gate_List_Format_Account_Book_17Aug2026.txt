1. LEDGER HOLDER DROPDOWN NOT SHOWING
-------------------------------------
Cause: the "Show In Ledger" handler un-hid the Ledger Holder wrapper but never
put a single <option> into the select, so it opened empty - which is what the
screenshot shows as "No results found". JournalController::create() already
passed $customers, $suppliers and $pump_operators to the view; nothing read
them. The Edit form had its own private copy of the populating code, which is
why the fault only ever appeared on Add.

Fix: both forms publish their lists onto their own modal, and one shared
function fills the select. Edit's private copy is gone, so the two cannot drift
apart again. A holder chosen earlier is preserved when it still exists in the
newly built list.

IF THE DROPDOWN IS STILL EMPTY AFTER THIS RELEASE, the cause is the database,
not the code. The ledger columns on `journals` are optional and were confirmed
missing on at least two tenants - see
Database/SQL/IS1992_Journals_Add_Ledger_Columns.sql, which has to be run once
per tenant database. That script is unchanged by this release. The screenshot in
this ticket was taken with Supplier Ledger selected, so please also confirm the
business actually has suppliers - an empty supplier list produces the same
"No results found" for a reason that is not a bug.


2. SUBMIT BUTTON SHOWING TOO EARLY
----------------------------------
"After selecting the Account, the Submit button should not be displayed
immediately. The Submit button should appear only after clicking the Add
button."

Submit is now hidden when the form opens and appears once Add has placed rows
into the entry table; it hides again if those rows are cleared. A short hint
sits where the button will be, so the form does not look broken while it is
absent.

This is VISIBILITY only. Whether Submit is ENABLED is still governed by the
existing checks - debit and credit totals matching, note, location and date -
so nothing about validation has been loosened.

The Edit form is deliberately unchanged: it opens with rows already present, so
hiding Submit there would only get in the way.


3. LIST JOURNAL ENTRY - FORMAT
------------------------------
The list now follows the reference layout:

  COLUMNS  #, Journal No, Date, Account, Ledger Holder, Debit, Credit, Note,
           Added By, Action.
           The row number is rendered in the browser and counts from 1 on the
           current page. Ledger Holder is new and resolves the customer,
           supplier or pump operator the entry is linked to.

  FILTERS  Ledger Holder and Status added alongside the existing Date Range,
           Account, Location and Entry Type.

  EXPORT   An Export button beside Add. It drives the CSV export the table
           already builds, so the file honours the filters and columns actually
           on screen rather than being a second export that has to be kept in
           step.

  ACTION   An "Actions" button opening View / Edit / Delete, using the same
           markup and Font Awesome icons as CustomerPaymentController and
           DisabledAccountController so it matches the rest of the system. View
           was previously missing altogether - show() was an empty stub - and is
           implemented here, returning a read-only view of the whole entry
           (every row sharing a journal_id, since a journal is only meaningful
           as a balanced set).

PERFORMANCE: ledger holder names are looked up ONCE per request and handed to
the row renderer. Resolving them per row would have added one query per row on
every draw of the list.

TWO POINTS THAT NEED YOUR CONFIRMATION
  a. STATUS. A journal has no posting status in this system - there is no
     draft/posted workflow and no status column on `journals`. The only state an
     entry carries is whether it is linked to a ledger, so the filter offers
     "Shown in Ledger" and "Not shown in Ledger". If Status was meant to mean
     something else, tell me what the values should be and it is a small change.

  b. FROM DATE / TO DATE. The reference image shows two separate date boxes. The
     page already has a working date-range picker that does the same job, and it
     has been kept rather than replaced. Say the word if the two-box layout is
     required.

  c. The reference image shows three plain icons in the Action column, while the
     ticket text asks for an "Actions" button with View/Edit/Delete inside. The
     text has been followed, since it is the more specific instruction and it
     matches the rest of the system.


4. ACCOUNT BOOK - DESCRIPTION
-----------------------------
Now produced in exactly the format the ticket gives:

    Transaction No: INV-000125 | Note: Fuel sales payment

One line, both halves labelled, separated by a pipe. IS2034 put them on separate
lines with no label on the note, which was not what was asked for.

Either half can be absent - a journal with no source document, a transaction
with no note - so the pipe only appears when there is something on both sides,
and a row with neither still shows "-".

Where the number comes from, most specific first: invoice_no, then ref_no, then
payment_ref_no. Journal rows reach the Account Book through
account_transactions.journal_entry with no parent transaction at all, so they
fall back to their journal number. slip_no is deliberately NOT used: it has its
own column and identifies a paying-in slip, so labelling it "Transaction No"
would put a wrong answer on screen rather than none.

The display expression is kept SEPARATE from the one used for filtering and
ordering, so no row can move into or out of the Account Book as a result of
this change.
