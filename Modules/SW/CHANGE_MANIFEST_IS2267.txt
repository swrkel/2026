1) Finance / List Accounts / Cash Deposit + Card Deposit / Daily Shift No
-------------------------------------------------------------------------
WHY THE PREVIOUS ATTEMPTS DID NOT FIX IT
The field shown in the Finance modal is NOT sw::partials.shift_field.
Finance owns a different select named "daily_shift_no".  Its deposit controller
historically fills the view variable $petroDailyShifts from PetroDailyShift.
Therefore repeated changes to SW's shared SW Shift No partial / shift-options
endpoint could never change the Daily Shift No dropdown shown in this Finance
modal.

ROOT FIX
- SWServiceProvider now attaches a view composer to Finance's existing deposit
  modal view (finance::account.deposit; account.deposit kept as legacy alias).
- At render time, after tenant middleware has selected the tenant DB, the
  composer reads the authoritative sw_shifts table for the ACTIVE business.
- Only semantically OPEN shifts are supplied to Finance's existing
  $petroDailyShifts variable.
- Shift::normalizeStatusValue(status, closed_at) is used, so both current
  numeric status values and older text status values are handled safely.
- closed_at is authoritative: a legacy row that still looks "open" but has a
  closed_at timestamp is NOT shown.
- soft-deleted shifts are excluded when deleted_at exists.
- No 500-row cap is used.
- Finance's existing modal AJAX uses a fresh request when opened, so opening a
  new SW shift appears on the next modal open and closing it removes it on the
  next modal open.
- No Finance source file is changed; Finance posting/calculation logic remains
  untouched.
- If SW is disabled for the business, Finance's original list is left untouched.

2) SW Settlement / New Settlement / Payments / Expenses / Expense Category
----------------------------------------------------------------------------
WHY THE PREVIOUS ATTEMPTS DID NOT FIX IT
Expenses New is standalone.  Expenses New / Categories / Add writes to:

    expnew_categories

The previous SW fixes kept refreshing / reading the legacy host table:

    expense_categories

The refresh/race/cache logic could therefore work perfectly and the newly added
Expenses New category would still never be returned, because it was asking the
wrong table.

ROOT FIX
- Added Services/ExpenseCategoryLookupService.php.
- expnew_categories is now authoritative whenever that table exists.
- The lookup matches Expenses New's own category option rule:
    business_id = active selected business
    is_active = 1 OR is_active IS NULL
    name IS NOT NULL
    ORDER BY name
- legacy expense_categories is used only as a compatibility fallback when the
  Expenses New category table genuinely does not exist.
- Initial settlement Blade options and live AJAX refresh now use the SAME lookup
  service, so they cannot disagree.
- Business resolution now follows Expenses New's multi-business convention:
  selected session business first, user's default business last.
- Removed the JavaScript fallback to /expense-categories/get-drop-down because
  that endpoint serves the legacy category master and could overwrite the
  correct Expenses New list.
- Existing one-request-at-a-time / Select2 opening race protection from IS2263
  is retained.
- Live endpoint remains no-store/no-cache and is refreshed when Expenses is
  selected/opened and when the page regains focus.
